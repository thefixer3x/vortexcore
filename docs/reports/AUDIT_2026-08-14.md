# VortexCore — Comprehensive Audit & Implementation Plan

**Date:** 2026-08-14
**Scope:** UX/Flow, Core Functionality, Subscription Billing, Security
**Goal:** Make VortexCore a seamless central finance hub that works for you, first.

---

## Executive Summary

VortexCore has solid infrastructure (Supabase schema, Stripe billing, AI chat, dashboard) but significant gaps between what exists in code and what the user actually experiences:

- **Signup is broken** — clicking "Create account" leads to a 404
- **No onboarding flow** — users land on an empty dashboard
- **Settings are mostly cosmetic** — only CurrencySheet works end-to-end
- **No free trial** — subscriptions work but trial is completely missing
- **Critical security gaps** — live secrets in repo, RLS negated, unauthenticated AI endpoints

## SECTION 3: Subscription & Payment (End-to-End)

### 3.1 Free Trial — **MISSING**

| # | Issue | Severity | Notes |
|---|-------|----------|-------|
| 3.1.1 | **No free trial configuration** — Zero trial support anywhere. `check-subscription` returns `status: "none"` for trialing users. `SubscriptionState` includes `"trialing"` type but nothing maps to it. | Critical | Add `trial_period_days` to checkout session creation |
| 3.1.2 | **No trial expiration handling** — No `customer.subscription.trial_will_expire` webhook handler. No grace period, no UI notification. | Critical | Add trial countdown UI + webhook handler |
| 3.1.3 | **No "trialing" status mapping** — Stripe sends `status: "trialing"` but `check-subscription` queries only `["active", "trialing"]` and the UI has no trialing-specific display. | Critical | Fix the mapping + add trial UI state |

### 3.2 Stripe Webhook — Gaps

| # | Issue | Severity | Notes |
|---|-------|----------|-------|
| 3.2.1 | **Missing `invoice.payment_failed` handler** — #1 event for payment failure detection is not handled. When subscription goes `past_due`, tier stays at "pro" but `can_use_advanced_models` becomes false — inconsistency with no user notification. | Critical | Add handler to downgrade tier + show "payment failed" warning |
| 3.2.2 | **No idempotency guard** — Stripe retries on 5xx. If webhook fails mid-stream, subscription row updates but tier row doesn't → inconsistent state. | Critical | The upsert pattern is safe, but add explicit event dedup logging |
| 3.2.3 | **No webhook dead-letter queue** — If webhook fails (DB outage), no alerting. Users silently get tier mismatch. | Medium | Write failed events to `webhook_logs` table + alerting |
| 3.2.4 | **Missing events** — `invoice.payment_succeeded`, `customer.subscription.paused`, `customer.updated`, `payment_method.attached` not handled. | Medium | Add handlers for payment recovery and payment method updates |

### 3.3 Payment Edge Cases

| # | Issue | Severity | Notes |
|---|-------|----------|-------|

| 3.3.2 | **No post-checkout state refresh** — Redirect URL has `checkout=success` query param but Settings page doesn't read it. User waits up to 10 minutes (polling interval) to see their new tier. | Medium | Add query param handler to force `refresh()` call |

| 3.3.6 | **user_tiers table may be missing** — Webhook references `user_tiers` but it's not in current migrations. May only exist in old backups. | Critical | **VERIFY IN PRODUCTION** — webhook will crash if table is missing |
| 3.3.7 | **Multiple subscriptions race condition** — `stripe_subscriptions` has no unique constraint on `customer_id`. User could have multiple active rows. | Critical | Add unique constraint + webhook to clean up stale rows |

## SECTION 4: Security Hardening

### 4.1 Infrastructure — **CRITICAL**

| # | Issue | Severity | Notes |
|---|-------|----------|-------|
| 4.1.1 | **`.env` with live secrets committed to repo** — `sk_live_` Stripe keys, Supabase `service_role` key, OpenAI/Gemini keys, Postgres/Redis/Kong passwords. `.gitignore` has `.env` but file IS tracked. | Critical | **IMMEDIATE:** Rotate every secret in `.env`. Remove file from git. Never commit again. |
| 4.1.2 | **`SUPABASE_SERVICE_ROLE_KEY` in client codebase** — Grants full read/write/delete on all tables, bypassing RLS. Should only exist on Edge Functions runtime. | Critical | Move to Supabase Vault. Remove from local `.env`. |
| 4.1.3 | **No `.env.example`** — No template showing which env vars are expected. | Minor | Create `.env.example` with placeholder values |

### 4.2 Authentication & Authorization

| # | Issue | Severity | Notes |
|---|-------|----------|-------|
| 4.2.1 | **`verify_jwt = false` for AI functions** — `ai-router`, `openai-assistant`, `openai-chat` have JWT verification disabled. Unauthenticated users can consume LLM quotas for free. | Critical | Set `verify_jwt = true` in `supabase/config.toml` |
| 4.2.2 | **`ai-router` has no rate limiting** — Open to the internet with no request caps. Attacker can hammer OpenAI/Gemini through your keys. | Critical | Add rate limiting (use `increment_edge_rate` RPC from migration) |
| 4.2.3 | **`auth-service` `requireAdmin` always returns false** — Hardcoded `const isAdmin = false`. No admin access possible. | Critical | Wire up real database lookup for admin roles |
| 4.2.4 | **`auth-service` `requirePermission` grants read/write to all users** — Hardcoded placeholder. All users effectively have full access. | Critical | Wire up real permission checks |
| 4.2.5 | **Role stored in `user_metadata` (client-settable)** — `AuthContext` reads `role` from `user_metadata`. User could manipulate via Supabase auth API. | High | Authoritative roles should be in a server-side table or `app_metadata` |
| 4.2.6 | **2FA enrollment can target any email** — `auth` edge function accepts `email` from request body and enrolls any user in 2FA. | High | Validate that requesting user owns the target email |

### 4.3 Row Level Security (RLS)

| # | Issue | Severity | Notes |
|---|-------|----------|-------|
| 4.3.1 | **`GRANT ALL ON ALL TABLES IN SCHEMA public TO authenticated`** — Both RLS migrations issue this. It negates all RLS policies for authenticated users via direct table access. | Critical | **Remove this line from ALL migrations.** It is the single most important RLS fix. |
| 4.3.2 | **`stripe` edge function returns full card details** — `get_card_details` returns PAN, CVC, expiry over HTTP. PCI compliance risk. | Critical | Remove `get_card_details` endpoint entirely. Card details should never leave Stripe's servers. |
| 4.3.3 | **Wildcard CORS on multiple functions** — `stripe`, `stripe-webhook`, `ai-router` all return `Access-Control-Allow-Origin: *`. | High | Restrict to known domains via proper CORS headers |

### 4.4 Data Protection

| # | Issue | Severity | Notes |
|---|-------|----------|-------|
| 4.4.1 | **No financial audit trail** — No audit log for who created/modified/deleted transactions, changed wallet balances, or modified subscriptions. PCI-DSS Requirement 10. | Critical | Create `financial_audit_log` table with trigger-based logging |
| 4.4.2 | **PII sent to LLMs without proper redaction** — `stripPII()` uses fragile regex. Users can paste bank account numbers into AI chat. | High | Implement more robust PII redaction. Consider local regex before sending to LLM |
| 4.4.3 | **`transactions` table stores PII in jsonb metadata** — `payload.email` and entire request object stored. | Medium | Store only necessary data. Remove raw payload from metadata |
| 4.4.4 | **CSP has `'unsafe-inline'` and `'unsafe-eval'`** — Weakens Content-Security-Policy significantly. | Medium | Remove `'unsafe-eval'` at minimum. Address `'unsafe-inline'` in scripts |

### 4.5 API Security

| # | Issue | Severity | Notes |
|---|-------|----------|-------|
| 4.5.1 | **In-memory rate limiting is no-op** — `callback-handler` and `payment` functions use `new Map()` for rate limiting. State is lost on every cold start. | High | Use Supabase `increment_edge_rate` RPC or Redis-backed rate limiting |
| 4.5.2 | **Callback handler uses plain string comparison for Bearer token** — Not timing-safe. Susceptible to timing attacks. | Medium | Use `timingSafeEqual` for all token comparisons |
| 4.5.3 | **Callback handler skips verification if no reference** — If `metadata.reference` is missing, transaction status is blindly accepted. | High | Always verify transaction with provider API regardless of reference field |
| 4.5.4 | **Edge functions expose detailed error messages** — Stack traces in `details` field of error responses. | Medium | Return generic error messages to client. Log details server-side |
